# AGENTS.md

## Repo overview

Unity game framework ("Fuel") with C# TCP server. Three top-level directories:

- `Client/UnityProject/TestProject/` — Unity project (the main workspace)
- `Server/C#Server/TestTcpServer/` — .NET 8 game server (GameServer)
- `Common/ExcelTool/` — Luban config table generation from Excel

## Key tech stack

- **Client**: Unity, HybridCLR (hot update), YooAsset (asset bundles), UniTask, ProtoBuf, Odin Inspector, DOTween
- **Server**: .NET 8, Serilog, Microsoft.Extensions.DI/Hosting, ProtoBuf, in-memory data layer (swap for EF/MongoDB in production)
- **Shared**: Luban (Excel → code), ProtoBuf (.proto → C#)

## Commands

### Luban config generation
```bat
cd Common\ExcelTool\Excels\DataTables
gen.bat
```
Runs `dotnet Luban.dll -t all -d json --conf luban.conf`. Outputs to `output/`. The `-t all` target includes both `client` (group `c`) and `server` (group `s`) outputs.

### Server build & run
```bash
cd Server/C#Server/TestTcpServer/TestTcpServer
dotnet build
dotnet run
```
Server listens on port 9000 by default (configurable in `appsettings.json`). Seeds two test accounts on startup: `testuser`/`test123` and `banneduser`/`ban123`.

### Client
Open `Client/UnityProject/TestProject/` in Unity Editor. No CLI build configured — use Unity's build pipeline.

## Architecture: Client

### Fuel framework (`Assets/Scripts/Fuel/`)
Core framework namespace. Key subsystems:

- **Launcher/** — Startup pipeline: `LoadLocalConfig → FetchRemoteVersion → CheckAppVersion → InitAssets → UpdateAssets → LoadAotMetadata → LoadHotUpdateDll → LoadConfigs → EnterGame`. See `StartupStep.cs` for enum. Pipeline is driven by `GameUpdatePipeline.cs`.
- **NetFramework/** — TCP networking with auto-reconnect, heartbeat (PING/PONG), message dispatching. `NetworkManager` is a `MonoSingleton`.
- **Manager/** — UIManager, AssetManager (YooAsset), AudioManager, SceneManager, EventDispatcher, CoroutineManager
- **Singleton/** — `MonoSingleton<T>` (MonoBehaviour) and `Singleton<T>` (plain class)
- **RedDot/** — Red dot notification system (has its own Editor + Runtime split)
- **Pool/**, **LocalData/**, **Log/**, **Tools/** — Utilities

### Game code (`Assets/Scripts/Game/`)
- `Config/Luban/` — Luban-generated C# config classes (DO NOT EDIT manually)
- `UI/{PanelName}/` — Each panel has a `NodeProvider` (generated) + `Window` (business logic)

### Generated code (`Assets/Scripts/Generated/`)
- `Proto/` — ProtoBuf-generated C# from `.proto` files. Shared with server.
- `Network/NetHandlerGenerated.cs` — Auto-generated from `[NetMessageHandler]` attributes. Regenerated by `NetHandlerAutoWatcher` on domain reload.

**DO NOT manually edit files under `Generated/`** — they are overwritten by codegen.

### Hot update (`Assets/HotUpdate/`)
- `Configs/Luban/` — Duplicate of Luban-generated classes for hot-update DLL context
- `Configs/TableKit.cs` — TableKit integration

### Config loading
`StartupConfig.json` in `Assets/Resources/` drives the launcher. Key fields: `appVersion`, `versionUrl`, `packageName`, `hotUpdateDllPath`, `hotUpdateEntryType`/`hotUpdateEntryMethod`.

## Architecture: Server

### Entry point
`Server/C#Server/TestTcpServer/TestTcpServer/Program.cs` — Generic host with DI.

### Structure
- `Core/Net/` — `GatewayServer` (TCP listener), `GameSession`
- `Core/Protocol/` — `FrameCodec`, `Packet`
- `Core/Routing/` — `MessageRouter`, `[MsgHandler]` attribute, `HandlerBase`
- `Core/Context/` — `PlayerStateCache`
- `Handlers/` — Message handlers (e.g., `LoginHandler`, `PingHandler`, `LogoutHandler`)
- `Data/` — Repository pattern: `IEntity`, `IRepository<T>`, `IUnitOfWork`, in-memory implementations
- `Services/` — `GatewayHostedService`, `HeartbeatService`
- `Proto/` — ProtoBuf-generated C# (mirrors client's `Generated/Proto/`)

### Adding a new server message handler
1. Add proto definition, generate C# into both client `Generated/Proto/` and server `Proto/`
2. Add command ID to `ProtoCmds.cs` (both client and server copies)
3. Create handler class inheriting `HandlerBase` with `[MsgHandler(ProtoCmds.YourCmd)]` attribute
4. Handler is auto-registered via assembly scanning at startup

## Code generation workflows

### ProtoBuf
`.proto` files → `protoc` → generated C# in both `Client/.../Generated/Proto/` and `Server/.../Proto/`. Keep both in sync.

### Net handler registration (client)
Mark static methods with `[NetMessageHandler(typeof(ResponseType))]` or `[NetMessageHandler(typeof(ResponseType), typeof(RequestType))]`. The editor tool `NetHandlerAutoWatcher` scans on domain reload and regenerates `Assets/Scripts/Generated/Network/NetHandlerGenerated.cs`.

### UI binding (client)
1. Create `UIBindData` asset via Odin editor
2. Run UIBindCodeGenerator → generates `{Name}NodeProvider.cs` (always overwritten) + `{Name}Window.cs` (first-time only, preserves business logic)
3. Bind to prefab via the editor window

### Luban config tables
Excel files in `Common/ExcelTool/Excels/DataTables/Datas/`. Schema in `__tables__.xlsx`, `__beans__.xlsx`, `__enums__.xlsx`. Run `gen.bat` to regenerate.

## Conventions

- **Language**: Code comments and commit messages are in Chinese (中文)
- **Namespaces**: Client framework = `Fuel.*`, Game code = `Game.*`, Server = `GameServer.*`
- **Singletons**: Use `MonoSingleton<T>` for MonoBehaviour singletons, `Singleton<T>` for plain C#
- **Async**: Client uses `UniTask` (Cysharp), server uses standard `async/await` with `CancellationToken`
- **Networking**: Client sends via `NetworkManager.Instance.Send<T>(msg)`, server handlers return responses via `session.SendAsync(packet, ct)`
- **Generated files**: Never edit `Assets/Scripts/Generated/` or `Assets/HotUpdate/Configs/Luban/` manually

## Pitfalls

- `Assets/HotUpdate/Configs/Luban/` duplicates `Assets/Scripts/Game/Config/Luban/` — this is intentional for HybridCLR hot-update context. Don't consolidate them.
- `ProtoCmdsLookup` uses `Type.GetType("ProtoCmds")` string lookup (not `typeof`) because ProtoCmds may live in the hot-update DLL. Don't change this to a hard type reference.
- The `.gitignore` excludes `*.csproj` and `*.sln` — these are Unity-generated and should not be committed.
- Server uses in-memory data (`InMemoryRepository`) — data is lost on restart. This is by design for development.
- `UIBindCodeGenerator` only generates `Window.cs` on first run. If you need to regenerate it, delete the existing file first.
- The `RedDot` system has an `Example~` directory (Unity hidden folder convention with `~` suffix).
